AltomateHR API

Read and write a company's HR and payroll data from your own system: employees, projects, claims, leave, attendance, overtime and payroll runs. Every request acts inside one company, with the permissions its API key was given.

Authentication

A company's admin creates an API key in AltomateHR. A key starts with wp_live_, belongs to one company, and is shown only once. Send it as a bearer token on every request: 

curl https://<api-host>/whoami \
  -H "Authorization: Bearer wp_live_xxx"
  • Every call is limited to the key's own company. There is no way to read or change another company's data with it.
  • A key acts with admin rights in that company, narrowed by its scopes.
  • An unknown or revoked key, or one whose company no longer exists, gets 401. The response doesn't say which, deliberately.
  • A key whose company has been deactivated by AltomateHR gets 401 on every endpoint, GET /whoami included, with a body that does say why: { "error": "This company's AltomateHR account has been deactivated. Please contact AltomateHR support.", "code": "company_deactivated" }. Don't retry: stop calling, and tell the company to contact AltomateHR support. Nothing is deleted, and the same key works again once the company is reactivated.
  • Some endpoints are for people only and answer 403 to any key: a person's own actions (clocking in, applying for leave, filing a claim or overtime, notifications), account actions (passwords, switching company) and platform settings (managing API keys and admin access, the activity log, accounting connections). The reverse also exists: POST /admin/admins and GET /admin/users are for keys only and answer 403 "This endpoint is for API keys only." to a signed-in person.
  • Every other endpoint needs a scope, listed on its page. Only GET /whoami and GET /pending work with any key.
Treat a key like a password: keep it on your server, never in a browser or app bundle. If one leaks, revoke it in AltomateHR and create a new one.

payroll:write covers creating and running payroll, adjustments, submitting, approving, rejecting and reverting runs, and payroll settings. A payroll run is money leaving a company, so only grant it to a system that needs it.

documents:read lists letter templates and letters on file and renders previews; documents:write edits templates and generates letters. A letter is filled from an employee's record, so the endpoints that touch one also need employees:read (and employees:write to save a missing detail back to the record). The Documents page lists exactly which.

Some areas are also part of a company's plan. If the plan doesn't include a module, its endpoints answer 403 with This organization's plan does not include the '…' module., whatever the key's scopes.

Errors

Errors come back as JSON in one of four shapes. Read the status code first.

StatusWhenBody
400A field failed validation{ "errors": { "Field": ["message"] } }
400 / 409The request is valid but not allowed now (e.g. a run that's no longer a draft, a month that already has an unnamed run){ "error": "message" }
400 / 404 / 409A business rule refused it, in some modules (Accounts, Attendance, Claims, Documents, Leave, Organization, Overtime, Policies, Teams) — each page says where{ "message": "…" }
401Missing, unknown or revoked keyempty
401The key's company has been deactivated. Match on code, not the wording{ "error": "…", "code": "company_deactivated" }
403Missing scope (including an employees:* scope a Documents action needs), module not in the plan, a people-only endpoint, or (for the two /admin endpoints) a signed-in person instead of a key{ "error": { "status": 403, "message": "…" } }
404Not found in this companyempty or { "error": "…" }

A robust client reads error when it's a string, error.message when it's an object, message when present, and the first entry of errors otherwise.

Conventions

  • JSON request and response bodies, with camelCase field names. Send Content-Type: application/json.
  • Ids are strings. Employees have two: the user id (from /employees) and the payroll profile id (employeeProfileId, from /payroll/employees). Payroll endpoints take the profile id; each endpoint page says which one it needs.
  • Enums are strings, such as "DRAFT" or "MONTHLY".
  • Names: name on /employees is always the legal name. Where an endpoint returns a person's name for display (the leave, claims, overtime and attendance lists, the admin attendance audit and the payroll run picker), a nickname, if one is set, is appended: "Jane Tan (JT)". Don't match people on those fields; use ids or GET /employees. Payslips and statutory files always use the legal name.
  • Money is a number with two decimal places, in Malaysian ringgit.
  • Dates are ISO 8601. A payroll month is given as periodYear + periodMonth (1–12).
  • Rate limits: none on the data endpoints today. GET /whoami is capped at 60 requests a minute per address and answers 429 above it, with a Retry-After header and a problem-details body that has no message field. POST /auth/verify is capped at 20 requests a minute per address, and also answers 429 when an account is locked or an IP is blocked for repeated wrong passwords. Keep calls sequential for writes to the same payroll run.

Check a key

GET /whoami No scope needed

What the key is and what it may do. Use it to confirm a pasted key belongs to the company you expect before storing it.

  "apiKeyId": "key_123",
  "tokenName": "Payroll converter",

  "features": ["onboarding.bulk", "sso.inbound", "auth.access"]

401 when the key is unknown, revoked, or its company no longer exists. A deactivated company's key also gets 401, with code: "company_deactivated" (see Authentication).

This endpoint also answers the platform master key (wp_master_), which first-party companion apps hold. That key belongs to no company, so it is told about none: kind: "master", the features list, and null for organizationId, apiKeyId, tokenName and role, with an empty scopes. Nothing else on this site accepts it — the endpoints it is for are not part of the company API.

429 when called more than 60 times a minute from one address.

Verify a person's password

POST /auth/verify No scope needed

Checks an email and password so your app can sign a person in before it starts its own session. Only the password is checked: no AltomateHR session, refresh token or login entry is created. Admins and owners only.

Send a company key (wp_live_), which answers only for that company, or the platform master key (wp_master_) held by first-party companion apps, which answers across the companies the person administers.

Request body

FieldTypeRequiredMeaning
emailstringyesThe person's email.
passwordstringyesThe person's password.
clientIpstringnoThe person's own IP address as your app saw it (max 64 characters, IPv4 or IPv6). Used only when you call with the master key; a company key ignores it. A value that isn't an IP address is ignored.

Response 200

FieldTypeMeaning
idstringThe person's user id.
namestringTheir name.
emailstringTheir email.
rolestringTheir role in the primary company.
organizationId, organizationNamestringThe primary company.
organizationsobject[]The companies they administer that you may ask about: id, organizationId, name, role.

Errors

StatusWhenBody
400A field is missing or too long{ "errors": { … } }
401Unknown or revoked key{ "message": "Invalid or revoked API key." }
401Wrong password, unknown email, not an admin, or an admin of a company you may not ask about. One answer for all four, on purpose.{ "message": "Invalid credentials for this organization." }
429The account is locked or the IP is blocked (see below){ "message": "…" } and a Retry-After header in seconds
429More than 20 requests a minute from one addressproblem-details body with no message field, and a Retry-After header
Lockouts. After 5 wrong passwords in a row for one email within 15 minutes, that account is locked for 15 minutes. While it is locked every attempt gets 429, even with the right password. A password reset ends the lock. After 10 wrong passwords within 15 minutes from one IP, that IP is blocked for 15 minutes, or for 1 hour if it was already blocked earlier the same day. Unknown emails are counted too, so a 429 never tells you whether an email exists. Which IP is counted depends on the key: with the master key, the clientIp you send, counted apart from sign-ins at AltomateHR itself (send none and no IP rule applies); while several attempts for one account are still being checked, a further one gets 429 with a "try again in a moment" message. With a company key, one shared bucket for that key, so one person guessing passwords through your app can lock your key's verifications for 15 minutes. Pass the person's real IP with a master key where you can, and stop retrying on 429: wait for Retry-After. 
curl -X POST https://<api-host>/auth/verify \
  -H "Authorization: Bearer wp_master_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "email": "jane@example.com", "password": "...", "clientIp": "203.0.113.7" }'
