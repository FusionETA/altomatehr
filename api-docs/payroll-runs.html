Payroll runs

One month of Malaysian payroll: create a run, generate payslips, adjust them, route them through approval, then file and pay. Every route on this page needs the Payroll module on the org's plan (403 otherwise) and either payroll:read or payroll:write — see Scopes.

The run lifecycle

A run moves through three statuses, one direction at a time (reject and revert step back):

DRAFT ──submit──> PENDING_APPROVAL ──approve──> SUBMITTED
  ^                      |                          |
  └───────reject─────────┘                          |
  └──────────────────revert───────────────────────────┘
  • Only a DRAFT run can be generated, adjusted, or have claims attached or detached. Once it moves to PENDING_APPROVAL or SUBMITTED those writes answer 409.
  • SUBMITTED is final. It is the only status that feeds next month's year-to-date figures, so getting there is guarded (see Submit for approval) and getting out of it cascades: reverting a month also reverts every later submitted month in the same year that reaches it through shared people, and sends later months awaiting approval back to draft (see Revert). An IMPORTED month (seeded by the YTD import) is never part of that cascade and cannot be reverted or generated itself — import it again to correct it.
  • Statutory files, the bank file, the run reports and payslip emails all require SUBMITTED. Two exceptions: the single payslip PDF and the run summary (PDF or Excel) can be downloaded before approval, as marked previews.
  • A month can hold several runs, but a person is in only one. A month may be split into runs for different staff groups (“Workers”, “Management”), each prepared, approved, filed and paid on its own. At most one run in a month may be unnamed, so POST /payroll/runs needs a name whenever the month already has an unnamed run (409 otherwise). Nobody is paid twice for a month: anyone already in another run that month is dropped from a new one, and left out of a re-run. Every run has its own id; the label (“October 2026 – Workers”) tells them apart, and a named run's file names carry its name (see Run names in file names).
  • Two employee ids. Every id on this page is an employeeProfileId from GET /payroll/employees or the picker below — not the user id GET /employees returns. Passing the wrong one reads back as "not found".
  • Generation is destructive. Pressing POST /{id}/generate discards the run's payslips and rebuilds them from the employees' current profiles. Adjustments and attached claims survive a regeneration; anything typed directly onto a payslip would not, which is why there is no such thing.
  • Staleness. The run object's isStale field is true when something an adjustment, a claim attachment or a profile edit touched has changed since the payslips were last generated. Submission is refused while it is true — re-run payroll first. A change to one person (an unpaid-leave or overtime approval) marks only the generated drafts that could hold them: a run whose chosen roster leaves that person out is not marked, and a run with no roster (everyone) is. Approving or reverting a run also marks the generated drafts of the later months of the same year stale (filed or pending runs are never marked), and so does approving, cancelling or editing unpaid leave: a change to an earlier, already-filed month is settled on the person's next run (see Generate), so those drafts were built from old figures. Run generate again on them.
Writes here move money and file paperwork with Malaysian authorities. Grant payroll:write only to a system that genuinely needs to run payroll, not just to read it.

Start a DRAFT run for a period. The id, status, totals and timestamps are the server's to set. A month can have several runs — see the rules for name below.

FieldTypeRequiredMeaning

A run object, with Location pointing at GET /payroll/runs/{id}.

The chosen roster is remembered. When the request sends at least one policyIds entry and resolves to at least one employee, the run stores the policyIds and excludedEmployeeProfileIds you sent, not just the resulting list of people — less anyone already in another run that month, who count as unticked, so they do not drift into this run if that other run is deleted. Generate uses them to pick up employees who become payable on those policies later. A run created from an explicit list (no policyIds, only exclusions), one that resolved to nobody, and one created before this was recorded store nothing: their roster stays exactly as frozen.
People already in another run that month are dropped, silently. The run is created with whoever is left; compare employeeCount or memberEmployeeProfileIds on the response with what you sent. Use the picker with year and month to see who is taken before you create.

PATCH /payroll/runs/{id} payroll:write

Change a run's settings: its name (in any status) or skipProration (DRAFT only). Only fields you send change.

Request body

FieldTypeRequiredMeaning
namestring or nullnoMax 60 characters (400 beyond that). Omitted or null: unchanged. "" (or blank) clears the name, which is refused while another run in the month is unnamed. Same uniqueness rules as on create. Allowed on a run in any status — it is only a label — and it does not mark the run stale. Sending the name the run already has changes nothing.

The updated run object.

Any skipProration on a run that is not a draft is a 409, and the whole request is refused — a name sent with it is not saved either.

Running payroll

POST /payroll/runs/{id}/generate payroll:write

"Run payroll": build every payslip on the run from the employees' current profiles. Safe to call repeatedly on a draft — each call discards the previous payslips and line items and rebuilds from scratch, folding in whatever adjustments and claims are on the run.

Unpaid leave decided after its month was filed is settled here. For each MONTHLY employee, generation looks at the earlier months of the same year that were computed and approved (SUBMITTED) here. If unpaid leave in one of them was approved after that month was run, or was cancelled or changed after being docked, the difference is added to this payslip as its own line item, priced at that month's salary ÷ its calendar days:

Line labelcategoryWhen
Unpaid Leave – Sep 2026 (approved late, 2 days)deduct_unpaid_leaveDays owed that were not docked in their own month. A deduction; it reduces the statutory bases like the ordinary Unpaid Leave line.
Unpaid Leave refund – Sep 2026 (1 day)wages_arrearsDays docked earlier that have since been cancelled or shortened. A payment (arrears of wages).

The month is written as the three-letter English month and year (Sep 2026); the day count is 1 day / 2 days / 1.5 days. A month can add one line of each kind. These days are not in the payslip's unpaidLeaveDays, which counts only the run's own month. The API returns the line only through the usual lineItems[] fields (label, category, amount); it does not expose which month a line settled as a separate field, so read it from the label. Months imported from a previous system, and months where unpaid days were typed on the run's adjustment, are never revisited. Once a run is approved, what it settled is final and is not settled again by a later run; reverting it to draft makes that provisional again.

The roster can grow on a re-run. If the draft was created with policyIds (POST /payroll/runs remembered them and excludedEmployeeProfileIds) and has never been approved, generating again adds anyone who has become payable on those policies since the draft was created — for example an employee transferred into a chosen policy, or a new hire — and memberEmployeeProfileIds in the response then includes them. This holds whatever skipProration is set to. Employees listed in excludedEmployeeProfileIds are never added, and nobody is ever removed from the roster by this. Anyone who is in another run that month is never added, and is left out of the payslips even if this run's roster still lists them. A run created without policyIds (e.g. from an explicit list, as an import does), a month reverted to draft after approval, and a run created before the roster was remembered keep their roster exactly as it was.

Approval

POST /payroll/runs/{id}/submit payroll:write

DRAFT → PENDING_APPROVAL. Most of this endpoint's value is in what it refuses:

  • The run has no payslips yet (press generate first).
  • The run is isStale — something changed after the last generation.
  • Any payslip's net pay is negative (exactly RM 0 is allowed).
  • The previous calendar month has no run, or has a run that is not yet SUBMITTED and that shares at least one person with this one — months must submit in order, because year-to-date figures compound off each filed month. The order is per person: a previous-month run for a different staff group does not hold this one up. A run's people are its roster plus anyone it has a payslip for; a run with neither (nobody chosen, nothing generated) counts as everyone, so it overlaps and blocks every other run.
  • Any earlier month of the same year has a run that is not yet SUBMITTED (draft or awaiting approval) and shares at least one person with this one — not only last month's. This is checked even when last month has no run at all, or has one for other people. Filing this month first would freeze those people's year-to-date without the earlier run, and would settle unpaid leave that run settles too. The earliest such month is named.
  • Readiness is not ok.

Response 200

The updated run object, now PENDING_APPROVAL.

Errors

  • 404 — no such run.
  • 409 { "error": "…" } — one of: already awaiting approval / already submitted / the guards above, each with its own message (e.g. "Submit December 2025 first — payroll runs are submitted in order, and that month's run is still a draft." or "Cannot submit — fix these first: …"). For an earlier month that is still open: "Submit March 2026 first — payroll runs are submitted in order, and that month's run for some of these people is still a draft." (the wording says “draft” even when that run is awaiting approval).
curl -X POST https://<api-host>/payroll/runs/run_123/submit \

POST /payroll/runs/{id}/approve payroll:write

PENDING_APPROVAL → SUBMITTED, by a different actor than the one who submitted (both are recorded on the run). If the org has opted into automatic Xero posting, this also posts the run's journal — best effort: a Xero failure here never un-approves the run.

Side effect: approving marks the generated drafts of the later months of the same year stale (isStale: true), because unpaid leave this run settled must not be settled a second time by a draft built before the approval. Re-run those drafts with generate before submitting them.

The updated run object.

SUBMITTED → DRAFT. Cascades: every later SUBMITTED run (a later month, same year) that shares a person with this one is reverted too, because their year-to-date figures were computed off this one. The reach is transitive: runs are walked in month order, and once a run is caught, its people count too. A September run for Ali reaches an October run for Ali and Ben, which in turn reaches a November run for Ben only. Year-to-date is per person, so a group that is never reached is left alone. A run with neither roster nor payslips counts as everyone, so it cascades to every later run, and is itself caught by any earlier run's revert. Other runs of the same month are never part of the cascade. Check revert-impact first to see what else will move.

Later runs awaiting approval are sent back to draft too. A later PENDING_APPROVAL run reached the same way is moved to DRAFT, its submission is cleared, and its approvalRejectionReason is set to "Sent back: the March 2026 payroll run was reverted to draft." (the reverted run's label). It needs a fresh generate before it can be submitted again. Later drafts that were already generated are marked stale (isStale: true) and need a re-run as well; they are not listed in alsoReverted.

Imported months are out of both ends of this. A run with source: "IMPORTED" cannot be reverted (409 below), and it is never pulled back by an earlier month's revert: its figures were typed in from the previous system, not computed off this year-to-date, so they stay SUBMITTED.
