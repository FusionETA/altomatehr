Leave

The company's leave types, each person's yearly entitlement and balance, leave applications (filing on someone's behalf, cancelling, the approval trail), reports and exports, and bulk import of leave history. Every endpoint on this page needs the organization's plan to include Leave — a key in a plan without it gets 403 with This organization's plan does not include the 'leave' module.

Read this first

  • Employee ids on this page are user ids — the id on each row of GET /employees (employees.html). Not the payroll profile id.
  • Years. Endpoints that take ?year= accept 2000–2100 and default to the current UTC year. Anything else is a 400 validation error.
  • Dates on a leave application are plain calendar dates (2026-03-02); timestamps (decidedAt, createdAt) are ISO 8601 UTC.
  • Days are numbers and may be halves (0.5).
  • Error bodies. Besides the shapes on the overview, this module's own refusals come back as { "message": "…" }. A missing scope or module is still { "error": { "status": 403, "message": "…" } }. The error tables below show the exact body.
  • Send a JSON body on every POST/PUT that lists one below, even when every field is optional — {} is enough. An empty body is a 400.
A key cannot be an approver. A key acts as an admin, but admins are not part of any approval chain — only people on a team seat are. So approve, bulk/approve, reject, cancellation/approve and cancellation/reject always refuse a key (403 You are not authorized to review this step, or a per-id failure in the bulk call). To settle leave with a key use file on behalf and admin cancel, which don't go through the chain. The approval endpoints are documented because they are reachable, so you know what to expect.
Acts as the caller. GET /leave, GET /leave/balances, GET /leave/team, GET /leave/team/balances and GET /leave/pending-count answer for "the person making the call". A key is not a person, so these return empty (or a meaningless default) for a key. Use GET /leave/all and GET /leave/balances/{employeeId} instead.

PUT /leave-types/{id} leave:write

Change a leave type. {id} is the leave type id.

This PUT replaces the whole type. PUT /leave/entitlements/{employeeId}/{leaveTypeId} leave:write

Override one person's entitlement for one leave type in one year — grant extra days or cut them. {employeeId} is the user id; {leaveTypeId} is from GET /leave-types.

Approvals and cancellation requests

Leave goes up the company's approval chain one layer at a time (set by teams and approval positions). Approved leave can later be cancelled in two ways:

  • The employee asks (people-only). The request goes up the same chain, layer by layer. While it is under review the leave stays APPROVED and its days stay taken; cancellationStatus is PENDING. The last layer's approval sets the leave to CANCELLED and the days come back. A rejection leaves the leave standing (cancellationStatus: "REJECTED"). The employee can only ask before the leave starts.
  • An admin cancels directly: admin cancel, any time, no chain.
Every endpoint in this section requires the caller to be an approver at the application's current step. A key never is, so a key always gets the refusal described in Read this first. They are listed so integrators know what they will see. To act on leave from an integration, use admin cancel or file on behalf.

POST /leave/cron/monthly-accrual leave:write

Run one monthly accrual: every PRO_RATED entitlement of the current Malaysian-time year gains one twelfth of its entitlement (capped at the full amount), and carried-forward days past their expiry are forfeited. No request body.
