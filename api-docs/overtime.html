Overtime

An overtime request is an employee's claim for extra hours on a work date, backed by a photo or PDF taken before the work and another taken after it. It moves through the employee's approval chain, and approved overtime is paid through that month's payroll run. These endpoints let you read requests and their files, look up the OT rate that applies on a date, and approve or reject.

Overtime requests

Needs the overtime module on the company's plan — every endpoint below answers 403 with This organization's plan does not include the 'overtime' module. otherwise.

Requests are filed by people (the employee submits, attaches the after-work file and can cancel) and there is no API-key route for any of that — see Not available to API keys. A key reads and, in principle, decides them.

A key can't act as an approver today. Approving and rejecting is allowed only for the people on the employee's approval chain at the request's current step (set up under teams). A key's identity is a synthetic id (apikey:…) that is never on a chain, so as the code stands approve and reject always answer 404, and bulk approve reports every id as failed. For the same reason GET /overtime (the caller's own requests) and GET /overtime/team (requests waiting on the caller) always return an empty array. Use GET /overtime/all and GET /overtime/{id} to read requests.

Read requests

GET /overtime/all overtime:read

Every overtime request in the company, newest work date first, whatever its status.

Response 200

An array of overtime request objects, with employeeEmail, employeeName, reviewerEmail and reviewerName filled in. Not paged: it returns the whole history, so cache it rather than polling. 

curl https://<api-host>/overtime/all \
  -H "Authorization: Bearer wp_live_xxx"
GET /overtime/{id} overtime:read

One request, by id, from anywhere in the company.

Response 200

An overtime request object. employeeEmail, employeeName, reviewerEmail and reviewerName are null here; take them from /overtime/all if you need them. 

curl https://<api-host>/overtime/ot_123 \
  -H "Authorization: Bearer wp_live_xxx"

Errors

404 (empty body) — no request with that id in this company.

GET /overtime overtime:read

The caller's own overtime requests, newest work date first.

"The caller" is a signed-in employee's own user id. An API key has no employee behind it, so with a key this always returns an empty array. Use GET /overtime/all.

Response 200

An array of overtime request objects (none for a key).

curl https://<api-host>/overtime \
  -H "Authorization: Bearer wp_live_xxx"
GET /overtime/team overtime:read

The requests currently waiting on the caller as an approver: every request, of any status, whose current approval step lists the caller.

A key is never on an approval chain, so with a key this always returns an empty array. Use GET /overtime/all.

Response 200

An array of overtime request objects, with employeeEmail and employeeName filled in (none for a key). 

curl https://<api-host>/overtime/team \
  -H "Authorization: Bearer wp_live_xxx"

OT rate

GET /overtime/rate overtime:read

Which overtime multiplier applies on a date, and why. It resolves the rate only — it doesn't compute any pay amount.

The rate is worked out for "the caller" (the employee's own policy and working days). A key isn't an employee, so with a key you get the company's default policy and a Monday–Friday working week, not any particular person's. It can't be pointed at an employee.

Request

Query parameterTypeRequiredMeaning
datestring (ISO 8601 date)yesThe day to classify, e.g. 2025-03-10.
projectIdstringnoA project, so a holiday set up for that project counts.

Response 200

FieldTypeMeaning
dayTypestring"NORMAL_DAY", "REST_DAY" or "PUBLIC_HOLIDAY". A public holiday that falls on a rest day is "PUBLIC_HOLIDAY" (the higher premium wins).
outOfShiftMultipliernumber | nullMultiplier for hours worked beyond the regular shift. Null when OT doesn't pay a cash premium (see reason).
inShiftMultipliernumber | nullPremium for hours worked within the regular shift on a rest day or public holiday. Always null on a normal day, where those hours are ordinary pay.
reasonstringPlain-English explanation, including why both multipliers are null: no policy resolved, OT disabled on the policy, or OT banked as time off instead of paid.
 
{
  "dayType": "REST_DAY",
  "outOfShiftMultiplier": 2.0,
  "inShiftMultiplier": 1.0,
  "reason": "Rest day (outside the employee's working days)."
}

  -H "Authorization: Bearer wp_live_xxx"

Approve and reject

These write endpoints need overtime:write. They decide a request as the approver at its current step — see the warning at the top of the page about what that means for a key.

Error bodies on this page's write endpoints use a fourth shape that the overview doesn't list: a 400 comes back as { "message": "…" }, not { "error": "…" }.
POST /overtime/{id}/approve overtime:write

Approve a pending request at its current step. On the last step of the chain the request becomes APPROVED; otherwise it stays PENDING and currentStep goes up by one for the next approver.

Response 200

The updated overtime request object. No request body.

Things that bite: the request must already have an after-work file; the decision notifies the employee; and a final approval marks any generated payroll draft that covers the work date's month as stale, so regenerate it before submitting that run. reviewerId is set on every step, not only the last. 
curl -X POST https://<api-host>/overtime/ot_123/approve \
  -H "Authorization: Bearer wp_live_xxx"

Errors

  • 404 (empty body) — no such request in this company, or the caller isn't the current-step approver. The two look the same on purpose. This is what a key always gets.
  • 400 { "message": "Only pending overtime requests can be approved or rejected." } — already decided or cancelled.
  • 400 { "message": "An after-work photo or file must be attached before approval." }
POST /overtime/bulk/approve overtime:write

Approve many requests in one call, each as the current-step approver. Every id is judged on its own, so one failure never blocks the rest. There is deliberately no bulk reject: a rejection needs its own remark, so reject one at a time.

Request body

FieldTypeRequiredMeaning
idsstring[]yesRequest ids; at least one. More than 200 and nothing is approved. Duplicates are counted once.

Response 200

Always 200 once the body is valid, even when every id failed. Read the per-id result.

FieldTypeMeaning
succeededintegerHow many ids were approved (or advanced a step).
failedintegerHow many were not.
itemsarrayOne entry per id: { id, ok, error }. error is the reason when ok is false.
 
{
  "succeeded": 1,
  "failed": 2,
  "items": [
    { "id": "ot_123", "ok": true, "error": null },
    { "id": "ot_124", "ok": false, "error": "An after-work photo or file must be attached before approval." },
    { "id": "ot_999", "ok": false, "error": "You can't approve this overtime request." }
  ]
}
curl -X POST https://<api-host>/overtime/bulk/approve \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "ids": ["ot_123", "ot_124"] }'
Things that bite: an id that doesn't exist, or that the caller can't decide, is reported as "You can't approve this overtime request." (what a key gets for every id); a request already decided gets the same reason as the single approve; a request with no after-work file is refused with its reason. Unlike the single approve, this does not send the employee a decision notification. A final approval still marks the payroll draft for the work date's month as stale. A list of more than 200 returns failed equal to the list length and one item with an empty id saying "Too many requests — pick fewer than 200."

Errors

400 { "errors": { "Ids": ["…"] } } — ids missing or empty.

POST /overtime/{id}/reject overtime:write

Reject a pending request at its current step. Final: a rejected request is not paid.

Request body

FieldTypeRequiredMeaning
reviewNotesstringyes, in practiceThe reason shown to the employee, up to 1000 characters. The field is optional in the schema but a blank or missing remark is refused.

Response 200

The updated overtime request object, with status: "REJECTED", reviewNotes, reviewerId and decidedAt set. The employee is notified. 

curl -X POST https://<api-host>/overtime/ot_123/reject \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "reviewNotes": "Hours do not match the site log." }'

Errors

  • 404 (empty body) — no such request, or the caller isn't the current-step approver. This is what a key always gets.
  • 400 { "message": "Only pending overtime requests can be approved or rejected." }
  • 400 { "message": "Enter a rejection remark before rejecting this overtime request." }
  • 400 { "errors": { "ReviewNotes": ["…"] } } — longer than 1000 characters.

Before and after-work files

The url of an attachment is a path on this API. Fetch it with the endpoint that matches its shape, sending the key as usual (prefix the path with the API host). An admin-level caller, which a key is, can open any file in the company; the response is the raw file with Cache-Control: no-store, and the file name comes back in Content-Disposition.

GET /overtime/photos/{fileName} overtime:read

A file stored by AltomateHR itself — the last segment of an attachment url of the form /overtime/photos/<fileName>.

Response 200

The file bytes, as image/jpeg, image/png, image/webp, image/heic, image/heif or application/pdf, chosen by the file extension. 

curl https://<api-host>/overtime/photos/20250310120000-ef56ab78.jpg \
  -H "Authorization: Bearer wp_live_xxx" \
  -o after.jpg

Errors

404 (empty body) — the file name isn't attached to any request in this company, or the file is no longer on disk.

GET /overtime/photos/xero/{xeroFileId} overtime:read

A file held in the company's Xero Files — an attachment url of the form /overtime/photos/xero/<fileId>. The API fetches it from Xero for you.

Response 200

The file bytes, with the content type and file name Xero holds for it.

curl https://<api-host>/overtime/photos/xero/xf_123 \
  -H "Authorization: Bearer wp_live_xxx" \
  -o job-sheet.pdf

Errors

404 (empty body) — the file id isn't attached to any request in this company, or Xero no longer returns it.

Not available to API keys

These are marked [HumanOnly] and answer 403 to any key: POST /overtime (submit), POST /overtime/photo (upload a file), POST /overtime/{id}/after-photo, DELETE /overtime/{id}/after-photo, DELETE /overtime/{id}/attachments/{attachmentId} and POST /overtime/{id}/cancel.
