Teams

A team belongs to one project and arranges its members in layers, from the bottom layer up. The layers above an employee are who approves that employee's claims, leave, overtime and attendance requests. These endpoints manage teams, who sits in which layer, and who exactly approves for a given employee.

How teams work

Needs the teams module on the company's plan — every endpoint below answers 403 with This organization's plan does not include the 'teams' module. otherwise.

  • Layers are numbered from 0 (the bottom) up to layerCount - 1. A request from someone at layer n goes to the members at layer n + 1, then n + 2, and so on. Any one member of a layer approving moves the request to the next layer.
  • Employee ids on this page are user ids — the id from GET /employees, not the payroll employeeProfileId.
  • Admins and owners are never approvers. They can be on a team's roster, but they are left out of every chain and every candidate list.
  • Empty layers are skipped. If nobody is eligible at a layer, the chain moves on to the next one.

The team object

FieldTypeMeaning
idstringTeam id.
projectIdstringThe project this team belongs to. Fixed when the team is created.
namestringDisplay name, unique within the project.
layerCountintegerNumber of layers, 1–6.
layerLabelsstring[]Names for the layers, bottom first, e.g. ["Staff", "Team Lead", "Manager"]. Returned exactly as saved. Where a label is missing or blank, chain and approver-option responses show "Layer N" (layer index plus one).
moduleApprovalConfigobjectWhich layers must approve, per module. Keys are module names (CLAIMS, LEAVE, OT, ATTENDANCE), values are arrays of layer numbers, e.g. { "LEAVE": [1, 2] }. A module that isn't listed is approved by all layers above the requester. A module listed with an empty array has no approval step at all.
membersarrayThe roster, highest layer first. Each entry is { employeeId, email, layer }. employeeId is the user id; email is null if it can't be resolved.
 
{
  "id": "team_123",
  "projectId": "prj_123",
  "name": "Site crew",
  "layerCount": 3,
  "layerLabels": ["Staff", "Team Lead", "Manager"],
  "moduleApprovalConfig": { "LEAVE": [1, 2] },
  "members": [
    { "employeeId": "emp_456", "email": "john@example.com", "layer": 2 },
    { "employeeId": "emp_123", "email": "jane@example.com", "layer": 0 }
  ]
}
Editing a team can approve pending requests. Updating or deleting a team, adding, moving or removing a member, and setting or clearing an approver override all re-check the company's pending claims, leave, overtime and attendance requests. Any request whose current approval step no longer has an approver is approved automatically (and the change is written to the activity log). This covers the whole company, not just the team you edited, and happens before the response returns. Creating a team does not do this. If the re-check itself fails, your edit is still saved and you still get the success response.
Error bodies on this page. A 400 for a rule the request broke (duplicate name, bad layer, ineligible approver, …) comes back as { "message": "…" } — note message, not the error key described on the overview. A 400 for a field that failed validation is still { "errors": { "Field": ["message"] } }. A 404 has an empty body.

Teams

GET /teams teams:read

Every team in the company, each with its roster.

Response 200

An array of team objects.

curl https://<api-host>/teams \
  -H "Authorization: Bearer wp_live_xxx"
POST /teams teams:write

Create a team in a project. The new team starts with no members.

Request body

FieldTypeRequiredMeaning
projectIdstringyesMax 40 characters. Not checked against the company's projects, so make sure it's a real project id from Projects.
namestringyesMax 120 characters. Surrounding spaces are trimmed. Must be unique within the project.
layerCountintegerno1–6. Defaults to 1.
layerLabelsstring[]noLayer names, bottom first. Defaults to none. Not checked against layerCount.
moduleApprovalConfigobjectnoSee the team object. Defaults to {} (every layer approves every module). Keys and layer numbers are saved as sent, without validation.

Response 200

The created team object. The status is 200, not 201.

curl -X POST https://<api-host>/teams \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "projectId": "prj_123",
    "name": "Site crew",
    "layerCount": 3,
    "layerLabels": ["Staff", "Team Lead", "Manager"],
    "moduleApprovalConfig": { "LEAVE": [1, 2] }
  }'

Errors

  • 400 { "errors": … } — a field is missing or out of range.
  • 400 { "message": "This project already has a team named \"…\"." }
PUT /teams/{id} teams:write

Rename a team and change its layers and approval config. The roster is edited separately, with the member endpoints.

Request body

FieldTypeRequiredMeaning
namestringyesMax 120 characters, trimmed, unique within the team's project (the team itself doesn't clash with its own name).
layerCountintegerno1–6. Defaults to 1 if you leave it out.
layerLabelsstring[]noReplaces the saved labels. Leaving it out clears them.
moduleApprovalConfigobjectnoReplaces the saved config. Leaving it out resets it to {}.
This replaces the whole team, it doesn't merge. Fetch the team first and send back every field you want to keep, or an omitted layerCount silently becomes 1. projectId can't be changed.
Lowering layerCount deletes every approver override on layers that no longer exist. Members already sitting on a removed layer are not moved or removed: fix their layer yourself. Pending requests left without an approver are approved automatically (see the warning at the top).

Response 200

The updated team object.

curl -X PUT https://<api-host>/teams/team_123 \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Site crew",
    "layerCount": 3,
    "layerLabels": ["Staff", "Team Lead", "Manager"],
    "moduleApprovalConfig": { "LEAVE": [1, 2] }
  }'

Errors

  • 400 { "errors": … } — a field is missing or out of range.
  • 400 { "message": "This project already has a team named \"…\"." }
  • 404 — no team with that id in this company.
DELETE /teams/{id} teams:write

Delete a team together with its whole roster and every approver override on it.

Everyone on the team loses the approval chain that came from it. Pending requests that then have no approver are approved automatically (see the warning at the top). This can't be undone.

Response 204

No body.

curl -X DELETE https://<api-host>/teams/team_123 \
  -H "Authorization: Bearer wp_live_xxx"

Errors

404 — no team with that id in this company.

Members

POST /teams/{id}/members teams:write

Add an employee to a team at a layer, or move someone already on it to a different layer. One employee has one row per team, so sending an existing member changes their layer.

Request body

FieldTypeRequiredMeaning
employeeIdstringyesThe employee's user id. Max 40 characters. Must belong to this company.
layerintegerno0–5, and below the team's layerCount. Defaults to 0 if you leave it out.
Only people whose role is Supervisor, Admin or Owner can sit above layer 0. A plain Employee is refused: everyone below them would route requests to someone who can't open the approvals screens. Change their role first (see Employees), then add them. Moving a member down a layer can leave requests without an approver, which triggers the automatic approval described at the top.

Response 200

The team object with its updated roster.

curl -X POST https://<api-host>/teams/team_123/members \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "employeeId": "emp_456", "layer": 2 }'

Errors

  • 400 { "errors": … } — employeeId missing or too long, or layer outside 0–5.
  • 400 { "message": "That layer doesn't exist on this team." } — layer is at or above the team's layerCount.
  • 400 { "message": "That employee doesn't exist in this organization." }
  • 400 { "message": "… is an Employee, so they cannot be placed above the bottom layer …" }
  • 404 — no team with that id.
DELETE /teams/{id}/members/{employeeId} teams:write

Take an employee off a team. Their approver overrides on this team are deleted with them, so adding them back later starts from the default.

Removing the last person from a layer empties it, and the chain skips empty layers, which shortens the path for everyone below. Pending requests left without an approver are approved automatically (see the warning at the top).

Response 200

The team object with its updated roster. Removing someone who isn't on the team is not an error; you get the unchanged team back. 

curl -X DELETE https://<api-host>/teams/team_123/members/emp_456 \
  -H "Authorization: Bearer wp_live_xxx"

Errors

404 — no team with that id.

Approval chains and approvers

For each layer above an employee, the people who approve are by default everyone else at that layer (administrators excluded). An override replaces that default for one employee at one layer with a hand-picked list.

GET /teams/chain/{employeeId} teams:read

Preview the approval chain an employee's requests would follow for one module, with the team's module config and any overrides applied.

Request

ParameterInRequiredMeaning
employeeIdpathyesThe employee's user id.
modulequerynoCLAIMS (default), LEAVE, OT or ATTENDANCE. Any other value is a 400 validation error.
projectIdquerynoPicks the team when the employee is on more than one. If it's missing or matches none of their teams, the team whose project name sorts first alphabetically is used.

Response 200

An array of steps, nearest approver first. The array is empty if the employee is on no team, already sits at or above the top approving layer, or the module is configured to skip approval. An unknown employeeId also gives [], not a 404.

FieldTypeMeaning
stepintegerPosition in the chain, from 0. Skipped layers don't leave gaps.
layerLabelstringThe layer's label, or "Layer N" if it has none.
approversarray{ employeeId, email } for each person who can approve at this step. Any one of them is enough.
 
[
  {
    "step": 0,
    "layerLabel": "Team Lead",
    "approvers": [
      { "employeeId": "emp_456", "email": "john@example.com" }
    ]
  }
]
curl "https://<api-host>/teams/chain/emp_123?module=LEAVE&projectId=prj_123" \
  -H "Authorization: Bearer wp_live_xxx"
GET /teams/{id}/members/{employeeId}/approver-options teams:read

For one team member, every layer above theirs: who could approve there, who does approve right now, and whether that's a custom list.

Response 200

An array with one entry per layer above the member's own, lowest first. It's empty for a member at the top layer.

FieldTypeMeaning
layerintegerLayer number.
layerLabelstringThe layer's label, or "Layer N".
candidatesarrayPeople who can be picked at this layer: the other members there, minus administrators. Each is { employeeId, email }.
effectiveApproverIdsstring[]User ids that approve at this layer right now: the override if there is one (limited to people still among the candidates), otherwise all the candidates.
isOverriddenbooleanTrue when a custom list is set for this member at this layer.
 
[
  {
    "layer": 1,
    "layerLabel": "Team Lead",
    "candidates": [
      { "employeeId": "emp_456", "email": "john@example.com" }
    ],
    "effectiveApproverIds": ["emp_456"],
    "isOverridden": false
  }
]
curl https://<api-host>/teams/team_123/members/emp_123/approver-options \
  -H "Authorization: Bearer wp_live_xxx"

Errors

404 — no such team, or the employee isn't a member of it.

PUT /teams/{id}/members/{employeeId}/approvers/{layer} teams:write

Choose exactly who approves for this employee at one layer, instead of everyone at that layer. {layer} is the layer number as an integer.

Request body

FieldTypeRequiredMeaning
approverIdsstring[]noUser ids of the approvers. Each must be a member of this team at exactly {layer} and not an administrator. Duplicates are dropped. Defaults to an empty list.
This replaces any earlier list for that employee and layer. An empty list is deliberate: nobody approves at this layer for this person, and the chain skips the layer. That is different from having no override, which means "everyone at the layer". Use the DELETE below to go back to the default. Leaving out approverIds counts as an empty list. Because an override changes who is asked next, pending requests left without an approver are approved automatically (see the warning at the top).

Response 200

The same array as approver-options, with the change applied.

curl -X PUT https://<api-host>/teams/team_123/members/emp_123/approvers/1 \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "approverIds": ["emp_456"] }'

Errors

  • 400 { "message": "That layer isn't above this employee's own layer." } — also returned when the layer is at or above the team's layerCount.
  • 400 { "message": "Every approver must be a member of this team at that exact layer." }
  • 404 — no such team, or the employee isn't a member of it. A {layer} that isn't an integer also gives 404.
DELETE /teams/{id}/members/{employeeId}/approvers/{layer} teams:write

Remove the custom approver list for this employee at one layer, so the default (everyone else at that layer) applies again.

Response 200

The same array as approver-options. Clearing a layer that has no override isn't an error. Like setting one, this can trigger the automatic approval described at the top. 

curl -X DELETE https://<api-host>/teams/team_123/members/emp_123/approvers/1 \
  -H "Authorization: Bearer wp_live_xxx"

Errors

404 — no such team, or the employee isn't a member of it.

Not available to API keys

None: every action in the teams controller can be called with a key that has the scope.
