Claims

A claim is an expense or mileage reimbursement an employee files for approval. Read a company's claims, export them, import historical ones, delete them, change the claims settings, and push approved claims to Xero.

Claims

Every endpoint on this page needs the claims module on the company's plan; without it they answer 403 with This organization's plan does not include the 'claims' module.

Filing claims is for people. Creating or editing a claim and uploading a receipt are not available to API keys (see the end of the page). To bring existing claims in from another system, use POST /claims/import.

Reading claims

GET /claims/all claims:read

Every claim in the company, whatever its status. This is the endpoint to read claims with from an API key.

Response 200

An array of claim objects, with employeeEmail, employeeName and awaitingApprovers filled in. There is no paging, filtering or guaranteed order: filter and sort on your side, or use the summary export to filter on the server. 

curl https://<api-host>/claims/all \
  -H "Authorization: Bearer wp_live_xxx"
GET /claims/{id} claims:read

One claim by id.

Response 200

A claim object. employeeEmail, employeeName and awaitingApprovers are not filled in here; take them from GET /claims/all if you need them. 

curl https://<api-host>/claims/clm_123 \
  -H "Authorization: Bearer wp_live_xxx"

Errors

404 (empty body) — no claim with that id in this company.

GET /claims claims:read

The caller's own claims.

An API key isn't an employee and has no claims of its own, so this always returns 200 with []. Use GET /claims/all. 
curl https://<api-host>/claims \
  -H "Authorization: Bearer wp_live_xxx"
GET /claims/team claims:read

The claims a supervisor has to decide, plus those their direct reports have already settled.

An API key is nobody's supervisor and is never in an approval chain, so this always returns 200 with []. Use GET /claims/all. 
curl https://<api-host>/claims/team \
  -H "Authorization: Bearer wp_live_xxx"

Receipts

A claim's receiptUrl (and each entry of supportingDocumentUrls) is a path on this API. Send it back to the matching endpoint below, with the same key, to download the file. Both answer with the file itself and Cache-Control: no-store, not JSON.

GET /claims/receipts/{fileName} claims:read

A receipt stored on the AltomateHR server, for a receiptUrl of the form /claims/receipts/20260115093000-a1b2c3d4.jpg.

Request

ParamInTypeMeaning
fileNamepathstringThe last segment of the claim's receiptUrl, extension included.

Response 200

The file. Content type is image/jpeg, image/png, image/webp, image/heic, image/heif or application/pdf, from the extension. 

curl https://<api-host>/claims/receipts/20260115093000-a1b2c3d4.jpg \
  -H "Authorization: Bearer wp_live_xxx" \
  -o receipt.jpg

Errors

404 (empty body) — no claim in this company references that file name, or the file is gone.

GET /claims/receipts/xero/{xeroFileId} claims:read

A receipt held in Xero Files, for a receiptUrl of the form /claims/receipts/xero/{xeroFileId}. AltomateHR fetches it from Xero for you, so you never need Xero credentials.

Response 200

The file, with the content type and file name Xero holds it under.

curl https://<api-host>/claims/receipts/xero/file_123 \
  -H "Authorization: Bearer wp_live_xxx" \
  -o receipt.pdf

Errors

404 (empty body) — no claim in this company references that file, or Xero can't serve it right now. The two look the same.

Claims settings

Three company-wide settings that decide when a claims run closes and how approved claims are paid.

The settings object

FieldTypeMeaning
claimRunCutoffDayintegerDay of the month, 1–28, that a claims run closes. A claim submitted on or before it belongs to that month's run; a later one rolls into the next. Defaults to 25.
settlementRoutestringXERO_BILL (default), PAYROLL or NONE (don't send anywhere). How approved claims are paid out.
xeroBillStagestringAwaitingPayment (default) or Draft. The stage a bill lands at in Xero. Only used on the XERO_BILL route.
GET /claims/settings claims:read

The company's current claims settings.

Response 200

The settings object.

{
  "claimRunCutoffDay": 25,
  "settlementRoute": "XERO_BILL",
  "xeroBillStage": "AwaitingPayment"
}
curl https://<api-host>/claims/settings \
  -H "Authorization: Bearer wp_live_xxx"
PUT /claims/settings claims:write

Change the company's claims settings. The change is recorded in the company's activity log.

Request body

FieldTypeRequiredMeaning
claimRunCutoffDayintegerno1–28. Defaults to 25 when omitted.
settlementRoutestringnoXERO_BILL, PAYROLL or NONE. Defaults to XERO_BILL when omitted.
xeroBillStagestringnoAwaitingPayment or Draft. Defaults to AwaitingPayment when omitted.

Response 200

The settings object as saved.

curl -X PUT https://<api-host>/claims/settings \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "claimRunCutoffDay": 20, "settlementRoute": "PAYROLL", "xeroBillStage": "Draft" }'

Things that bite

  • It replaces all three settings. A field you leave out is reset to its default, not kept. To change one setting, read GET /claims/settings first and send all three back.
  • settlementRoute applies to claims filed afterwards. Each claim carries the route it was filed under, so switching it doesn't re-route claims that already exist. Company-paid claims never use PAYROLL: under the PAYROLL route they are stamped XERO_BILL (Spend Money) if Xero is connected, otherwise NONE; only own-money claims are reimbursed through payroll. xeroBillStage, by contrast, is read each time a claim is pushed to Xero.

Errors

  • 400 { "errors": { … } } — claimRunCutoffDay outside 1–28 (Cutoff day must be between 1 and 28.), or an unknown enum value.
  • 404 (empty body) — the company no longer exists.

Deleting a claim

DELETE /claims/{id} claims:write

Permanently delete a claim.

Response 204

No body.

curl -X DELETE https://<api-host>/claims/clm_123 \
  -H "Authorization: Bearer wp_live_xxx"

Things that bite

  • Any status can be deleted, approved and rejected claims included. There is no undo.
  • Xero is not touched. A bill already pushed to Xero stays there; void it in Xero yourself.
  • The claimant's and approvers' open screens are told to refresh.

Errors

404 (empty body) — no claim with that id in this company.

Approving and rejecting

These never succeed for an API key. Only the person who is the claim's current approver in the claimant's team chain can decide it, and an API key is never in a chain. Single approve and reject answer 404 for every claim; bulk approve answers 200 with every id failed. The endpoints are listed because a key with claims:write reaches them, so you know not to build on them. Approve and reject claims in the AltomateHR app.
POST /claims/{id}/approve claims:write

Approve a claim as its current-step approver. Moves it to the next step, or to APPROVED on the last one (which then pushes it to Xero when the company pays on the XERO_BILL route).

Response 200

The updated claim object.

Errors

  • 404 (empty body) — no such claim, or the caller isn't its current approver. This is what a key always gets.
  • 400 { "message": "Only pending claims can be approved or rejected." }
curl -X POST https://<api-host>/claims/clm_123/approve \
  -H "Authorization: Bearer wp_live_xxx"
POST /claims/{id}/reject claims:write

Reject a claim as its current-step approver. A rejection is final and needs a remark.

Request body

FieldTypeRequiredMeaning
reviewNotesstringyesWhy it was rejected, up to 2000 characters. Shown to the claimant.

Response 200

The updated claim object, status REJECTED.

Errors

  • 404 (empty body) — as for approve. This is what a key always gets.
  • 400 { "errors": { … } } — reviewNotes missing or over 2000 characters.
  • 400 { "message": "…" } — the claim is no longer pending, or the remark is blank.
curl -X POST https://<api-host>/claims/clm_123/reject \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "reviewNotes": "Receipt is unreadable" }'
POST /claims/bulk/approve claims:write

Approve many claims in one call, each judged on its own. There is no bulk reject: a rejection needs its own reason.

Request body

FieldTypeRequiredMeaning
idsstring[]yesClaim ids. At least one; more than 200 is refused whole.

Response 200

Always 200, even when every id failed. Read the report.

FieldTypeMeaning
succeeded, failedintegerCounts.
itemsarrayOne entry per distinct id: { id, ok, error }. error is null when ok. A claim over its spend limit always fails here (Over the spend limit — approve this one on its own after reading it.).
 
{
  "succeeded": 0,
  "failed": 1,
  "items": [
    { "id": "clm_123", "ok": false, "error": "You can't approve this claim." }
  ]
}
curl -X POST https://<api-host>/claims/bulk/approve \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "ids": ["clm_123", "clm_456"] }'

Errors

  • 400 { "errors": { … } } — ids missing or empty.
  • More than 200 ids is not an error status: you get 200 with succeeded: 0, failed set to the number sent, and one item with an empty id and the error Too many claims — pick fewer than 200.

Pushing to Xero

An approved claim is pushed to Xero automatically when the final approver signs it off and the company pays on the XERO_BILL route. These endpoints do it by hand, for claims that failed, were imported already approved, or were never pushed. A personal-paid claim becomes a bill, a company-paid one a spend-money transaction. They write into the company's accounting system, so they need a Xero connection set up in AltomateHR.

POST /claims/{id}/xero-sync claims:write

Push one approved claim to Xero.

Request body (optional)

FieldTypeRequiredMeaning
statusstringnoAwaitingPayment or Draft: the stage the bill lands at. Omit it (or send no body) to use the company's xeroBillStage setting.

Response 200

FieldTypeMeaning
alreadySyncedbooleantrue when the claim already had a Xero document. Nothing was sent; this is not an error, so a retry can never create a second bill.
claimobjectThe claim object, with xeroSyncStatus, xeroBillId and xeroBillRef set.
 
curl -X POST https://<api-host>/claims/clm_123/xero-sync \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "status": "Draft" }'

Errors

  • 404 (empty body) — no claim with that id in this company.
  • 400 { "message": "…", "claim": { … } } — it wasn't pushed, and message says why: the claim isn't approved; it's routed to payroll (This claim is set to be reimbursed through payroll…); its account or company bank account doesn't exist in Xero; or Xero refused it or isn't connected. For the Xero-side failures the claim's xeroSyncStatus becomes ERROR and xeroSyncError holds the reason.

Things that bite

  • Only APPROVED claims can be pushed.
  • A claim with settlement PAYROLL is refused, so it can't be paid twice. It is reimbursed through payroll instead.
POST /claims/bulk/xero-sync claims:write

Push many approved claims to Xero in one call. They are sent one after another, each judged on its own.

Request body

FieldTypeRequiredMeaning
idsstring[]yesClaim ids. At least one; more than 200 is refused whole.
statusstringnoAwaitingPayment or Draft, applied to every claim. Omit to use the company setting.

Response 200

Always 200: { succeeded, failed, items } with one { id, ok, error } item per distinct id, as for bulk approve. A claim that was already pushed counts as ok. An unknown id fails with Claim not found. 

{
  "succeeded": 1,
  "failed": 1,
  "items": [
    { "id": "clm_123", "ok": true, "error": null },
    { "id": "clm_456", "ok": false, "error": "Only approved claims can be billed to Xero." }
  ]
}
curl -X POST https://<api-host>/claims/bulk/xero-sync \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "ids": ["clm_123", "clm_456"] }'

Errors

400 { "errors": { … } } — ids missing or empty. More than 200 ids gives 200 with every id counted as failed and a single item (empty id) saying Too many claims — pick fewer than 200.

Export and import

The export endpoints answer with a file, not JSON. format is csv (the default, also used for any value that isn't recognised), xlsx (or excel) or pdf. The response's Content-Type and Content-Disposition follow the format, and it carries Cache-Control: no-store.

GET /claims/export/summary claims:read

Every claim, as a spreadsheet or printable report, optionally filtered. Employees, projects and accounts appear as names, not ids.

Request

ParamTypeMeaning
formatstringcsv, xlsx or pdf.
from, todate (ISO 8601)Both inclusive, compared by calendar day. Either can be left out. With no dates at all, every claim is exported.
dateFieldstringWhich date from/to and the sort apply to: spent (default) or submitted. Up to 20 characters; any other value behaves as spent.
statusstringSUBMITTED, PENDING, APPROVED or REJECTED.
paymentTypestringPERSONAL or COMPANY.
employeeIdstringThe claimant's user id, up to 40 characters.
projectIdstringUp to 40 characters.

Response 200

The file, newest first. It is named claims-summary-{from}-to-{to}.{ext} when both dates are given, otherwise claims-summary-{today}.{ext}. CSV and XLSX have one row per claim and these columns: Claim #, Employee, Employee Email, Title, Description, Claim Type, Category, Payment Type, Amount, Currency, Spent On, Submitted On, Status, Approval Step (counted from 1), Project, Account Code, Account Name, Merchant, Spending With, Over Limit, Distance, Mileage Rate, Review Notes. The PDF is a narrower report (12 columns) with the filter described under the title and totals per currency. 

curl "https://<api-host>/claims/export/summary?format=csv&from=2026-01-01&to=2026-01-31&status=APPROVED" \
  -H "Authorization: Bearer wp_live_xxx" \
  -o claims.csv

Errors

400 { "errors": { … } } — a date that doesn't parse, an unknown status or paymentType, or an over-long text parameter.

GET /claims/export/payroll claims:read

The payroll reimbursement run: approved, personal-paid claims routed to payroll, totalled per employee, for one month's run.

Request

ParamTypeMeaning
formatstringcsv, xlsx or pdf.
monthstringThe run, as yyyy-MM, e.g. 2026-01. Omit it for the run currently open. A value that isn't yyyy-MM is treated as omitted, not rejected.

Response 200

The file, named payroll-reimbursements-{yyyy-MM}.{ext}, with one row per employee and currency: Employee, Employee Email, Claims (a count), Claim #s, Total Amount, Currency, Run Month, and a totals row. 

curl "https://<api-host>/claims/export/payroll?format=xlsx&month=2026-01" \
  -H "Authorization: Bearer wp_live_xxx" \
  -o reimbursements.xlsx

Things that bite

  • A run is not a calendar month. It covers claims submitted from the day after the previous month's cutoff to the cutoff day inclusive. With a cutoff of 25, the 2026-01 run is 26 December to 25 January.
  • Only claims whose settlement is PAYROLL appear, so company-paid claims never appear, and an empty file usually means the company pays through Xero, or settlementRoute was changed after the claims were filed.

POST /claims/import claims:write

Bring historical claims in from another system. It adds claims and never changes or removes one, so uploading the same file again is safe.

Request

multipart/form-data with one file field named file: a .csv or .xlsx of at most 8 MB. Headers are matched ignoring case, spaces and punctuation, and a few synonyms are accepted (Email, Date, Total…). Start from the template.

ColumnRequiredMeaning
Employee Emailone of these twoIdentifies the claimant. A name that matches more than one employee fails the row, so prefer the email.
Employee Name(see above)Used when there is no email.
TitleyesUp to 200 characters.
CategoryyesTRAVEL, TRANSPORT, MEAL, MEDICAL, WELLNESS, HARDWARE, OFFICE or OTHER.
AmountyesGreater than 0. Rounded to 2 decimals and stored exactly as given, never recalculated.
Spent OnyesA date. 2026-01-15 is canonical; dd/MM/yyyy also works.
CurrencynoThree letters. Defaults to MYR.
StatusnoSUBMITTED, PENDING, APPROVED or REJECTED. Blank means APPROVED; an unrecognised value fails the row.
Claim TypenoEXPENSE or MILEAGE. Blank or unrecognised becomes EXPENSE.
Payment TypenoPERSONAL or COMPANY. Blank or unrecognised becomes PERSONAL.
Account CodenoThe code of a chart-of-accounts entry. A code the company doesn't have fails the row.
DescriptionnoFree text.
Review NotesnoFree text.
Claim #noYour own reference, up to 40 characters. Generated when blank.

Response 200

FieldTypeMeaning
importedintegerClaims added.
skippedintegerRows already there (see below) and the template's example row. Not a failure.
failedintegerRows that couldn't be imported.
errorsarray{ row, message } for each failed row, at most 200. row is the spreadsheet row, header = 1, first data row = 2.
warningsarraySame shape, for rows that landed but deserve a look.
 
{
  "imported": 98,
  "skipped": 1,
  "failed": 1,
  "errors": [
    { "row": 14, "message": "No employee in this organization matches 'jane@example.com'." }
  ],
  "warnings": []
}
curl -X POST https://<api-host>/claims/import \
  -H "Authorization: Bearer wp_live_xxx" \
  -F "file=@claims.csv"

Things that bite

  • It is 200 even when rows failed. Check failed and errors, not the status.
  • A file the importer can't read is also 200. An empty file, a header row with no data rows, or a missing required column comes back with imported: 0, failed: 0 and a single entry in errors at row 1. Check errors too.
  • A row is skipped as a duplicate when its Claim # already exists, or, with no Claim #, when the same employee, spent date, amount and title already exist. Skipped rows are never updated.
  • Imported claims aren't re-checked. Spend limits, mileage rules and the approval chain are not applied, and nothing is pushed to Xero. A blank Status imports as already approved.
  • Imported claims are routed to Xero (settlement XERO_BILL) whatever the company's route is, so they never appear in the payroll export.
  • Imported claims have no project and no receipt, and submittedAt is the spent date.
  • Everyone in the company's open screens is told to refresh once the import finishes.

Errors

  • 400 { "message": "Pick a .csv or .xlsx file to import." } — no file, or an empty one.
  • 400 { "message": "Unsupported file type. Upload a .csv or .xlsx file." }
