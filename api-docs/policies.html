Policies

Employee policies (attendance rules, overtime, leave entitlements) and the one-call bulk setup an integration sends when it provisions a company.

Policies

A policy is a bundle of rules an employee is put on: which self-service areas they can use, how clock-in is checked, how overtime is calculated and paid, and how many days of each leave type they get. Everyone not assigned a policy falls back to the company's default policy. A new company starts with two, Monthly Workers and Hourly Workers.

PUT /policies/{id} replaces the whole policy. Any field you leave out goes back to its default (see the table below), including every switch and every overtime rate (an omitted rate becomes null, the company's rate), and leaveEntitlements is replaced by what you send, so omitting it empties the policy's entitlements. The one exception is overtimeRates, where omitting it leaves the list as it is. Read the policy with GET /policies, change what you need, and send the whole thing back.
Keys are not restricted. A key with policies:write may call every endpoint below. A signed-in person is different: only the organization's owner may create, archive or restore a policy or choose the default, and an admin gets 403 on those. An admin may edit a policy (PUT) only if their employee scope covers it. Those 403s and the 404 on PUT are therefore for people, not keys, and are listed under each endpoint for completeness.

Policy endpoints:

GET /policies policies:read

The policies the caller may see, archived ones included, ordered by name. For an API key that is every policy in the company. (A signed-in admin limited to some policies sees only those; a key is never limited.)

Module gate: the policies module, held to the plan only. Other screens use this as a lookup, so no per-admin grant is checked.

Errors

  • 400 a field failed validation ({ "errors": { … } }), e.g. a missing or over-long name, or a value outside its range.
  • 400 { "message": "A policy named \"Office Staff\" already exists." }. Note this shape: message, not error.
  • 400 { "message": "\"ot_type_123\" isn't one of the company's own overtime types." } an overtimeRates entry names an id that is not a custom type of this company (a built-in type, an unknown id or another company's). { "message": "Each overtime type can be listed once." } for a repeated id.
  • 403 the key lacks the scope, or the plan lacks the module.
  • 403 { "error": { "status": 403, "message": "Only the organization's owner can create a policy. …" } } a signed-in admin of any kind called this; only the owner may. Never returned to a key.
PUT /policies/{id} policies:write

Replace a policy's settings and leave entitlements.

Module gate: the policies module. A plan without it gets 403. Policies is not a per-admin grant, so for a key only the plan matters.

Request

id in the path is the policy id. The body is the same as POST /policies.

This is a full replace, not a merge: omitted fields revert to the defaults listed for POST /policies (the three otRate… fields go back to null, the company's rate, so a policy's own multiplier is lost unless you send it again), and leaveEntitlements is replaced wholesale (an omitted or empty list removes them all). overtimeRates is the exception: omitted or null keeps what is there, and a list replaces it. It does not change isDefault or isArchived; use the endpoints below for those.

Response 200

The updated policy, as for POST /policies.

curl -X PUT https://<api-host>/policies/policy_123 \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Office Staff",
    "salaryType": "MONTHLY",
    "otRateNormalDay": 1.5,
    "leaveEntitlements": [{ "leaveTypeId": "leavetype_123", "defaultDays": 16 }]
  }'

Errors

  • 400 a field failed validation ({ "errors": { … } }), e.g. a missing or over-long name, or a value outside its range.
  • 400 { "message": "A policy named \"Office Staff\" already exists." }. Note this shape: message, not error. Another policy already has that name.
  • 400 { "message": "\"ot_type_123\" isn't one of the company's own overtime types." } or { "message": "Each overtime type can be listed once." } a bad overtimeRates entry, as for POST /policies.
  • 400 { "message": "The name \"Office Staff\" isn't available. Choose another." } the name is taken by a policy the caller can't see (only a signed-in admin limited to some policies gets this wording; it never names the hidden policy).
  • 404 no policy with that id in this company (empty body). A signed-in admin limited to some policies also gets this for a policy outside their scope, so it doesn't confirm the policy exists.
  • 403 the key lacks the scope, or the plan lacks the module.
  • 403 { "error": { "status": 403, "message": "This policy also applies to the company's admins or owner, so only the owner can change it." } } a signed-in admin limited to some policies edited a policy that covers the company's admins or owner. Never returned to a key.

Bulk setup

One call that sets a company's working days, pay calculation, overtime rates, working hours and leave entitlements, for an integration that has just created the company and collected the client's answers. Every block is optional; send only what the client answered.

PUT /onboarding organizations:write policies:write leave:write

Apply the company's initial policy, working-time and leave setup in one request.

Scopes: the key needs all three scopes above, not one of them. Module gate: none, so it works whether or not the plan includes the Policies module.

Check for support first. A deployment advertises this endpoint by listing onboarding.bulk in features on GET /whoami. Probe that before relying on it, rather than finding out from a failed call.

Request

A JSON object with up to five optional blocks: settings, calculation, overtime, workSchedule, leave. The fields below are written as block.field.

FieldTypeRequiredNotes
settings.workingDaysstring[]NoWeekday names that are worked, e.g. ["MONDAY", …]. Case-insensitive. Send this or nonWorkingDays, never both.
settings.nonWorkingDaysstring[]NoWeekday names that are not worked; the rest become working days.
calculation.prorationBasisstringNoTWENTY_SIX or CALENDAR (case-insensitive): the day count a month is divided into when pro-rating pay.
calculation.hrdf.contributebooleanNoWhether the company contributes to HRDF.
calculation.hrdf.ratenumberWhen contribute is trueMust be greater than 0 when contributing.
overtime.normalDay, overtime.restDay, overtime.publicHolidaynumberNoOvertime multipliers. Same names and meaning as otRateNormalDay etc. on GET /policies, without the ot prefix. Only the ones you send are changed. No range check is applied here. The in-shift multipliers (restDayInShift, publicHolidayInShift) no longer exist: sending them is harmless and they are ignored.
overtime.dailyThresholdMinutesnumberNoAccepted but not applied by the current code (see the note below).
workSchedule.workingHoursStart, workSchedule.workingHoursEndstringNoStored as sent (the default is "09:00" and "18:00"). Empty strings are ignored.
workSchedule.lunchBreakMinutesnumberNoMinutes.
leave.entitlementsobjectNoMap of leave-type code to default days per year, e.g. { "ANNUAL": 16 }. Codes are case-insensitive.
leave.carryForwardobjectNoMap of leave-type code to { "enabled": boolean, "expiryMonth": number, "maxDays": number }. expiryMonth is 1 to 12 and required when enabled is true. When enabled is false, the stored expiry month and max days are cleared.

Response 200 or 409

200 when every block you sent was applied; 409 when at least one failed. Both carry the same body:

FieldTypeMeaning
appliedstring[]Blocks that were written, from settings, calculation, overtime, workSchedule, leave.
failedstring[]Blocks that threw and were not written. Empty on 200.
policiesUpdatedstring[]Ids of the policies the overtime block touched.
leaveTypesUpdatedstring[]Codes of the leave types the leave block changed.
 
{
  "applied": ["settings", "overtime", "leave"],
  "failed": [],
  "policiesUpdated": ["policy_123", "policy_456"],
  "leaveTypesUpdated": ["ANNUAL"]
}

Things that bite

It is not atomic. Blocks run in a fixed order (settings, calculation, overtime, workSchedule, leave) with no surrounding transaction, and one failing does not stop the rest. On a 409, the blocks listed in applied did land. Fix the cause and re-send the same body: every block is idempotent, so the ones that already applied simply apply again.
Overtime goes to every non-archived policy, not just the default. A new company has two policies (monthly and hourly), and setting rates on one would leave the other on the company's rates. The numbers are written as each policy's own multiplier; they do not change the company's overtime types (Overtime types), and the block can't set a company's own (custom) types. That also makes this a provisioning tool: after go-live, use PUT /policies/{id} per policy, because re-sending this would flatten policies an admin set apart on purpose.
  • The body is checked before anything is written. A bad request returns 400 and changes nothing.
  • An empty body {} returns 200 with empty lists.
  • Leave codes that don't match one of the company's leave types are skipped silently, with no error. Check leaveTypesUpdated to see what was matched. A new company starts with ANNUAL, MEDICAL, COMPASSIONATE, HOSPITALIZATION, MARRIAGE, MATERNITY, PATERNITY and UNPAID.
  • The leave block writes the leave types directly. It does not run the checks the leave-type endpoints make (such as carry-forward only on ANNUAL, or no negative days), so a value you send is stored as sent.
  • overtime.dailyThresholdMinutes is accepted in the body but the current code does not write it to any policy. Set the threshold with PUT /policies/{id} (otDailyThresholdMinutes).
  • The settings block writes working days to the organization; the calculation block writes the pro-rating basis and HRDF settings to the payroll settings, creating them if the company has none yet.
curl -X PUT https://<api-host>/onboarding \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "settings": { "nonWorkingDays": ["SATURDAY", "SUNDAY"] },
    "calculation": { "prorationBasis": "TWENTY_SIX", "hrdf": { "contribute": true, "rate": 1.0 } },
    "overtime": { "normalDay": 1.5, "restDay": 2.0, "publicHoliday": 3.0 },
    "workSchedule": { "workingHoursStart": "09:00", "workingHoursEnd": "18:00", "lunchBreakMinutes": 60 },
    "leave": {
      "entitlements": { "ANNUAL": 16, "MEDICAL": 14 },
      "carryForward": { "ANNUAL": { "enabled": true, "expiryMonth": 3, "maxDays": 5 } }
    }
  }'

Errors

  • 400 { "message": "…" } the body was refused before anything ran: both workingDays and nonWorkingDays sent; a name that is not a weekday; hrdf.rate not above 0 when contribute is true; an unknown prorationBasis; expiryMonth missing on an enabled carry-forward. Note message, not error.
  • 400 { "errors": { … } } expiryMonth outside 1 to 12.
  • 409 some blocks applied and some failed. The body is the response above, not an error object.
  • 403 the key lacks one of the three scopes.

Overtime types

An overtime type is a kind of overtime the company pays, with a company-wide multiplier (times the hourly rate). Three are built in and always exist: a normal day, a rest day and a public holiday. Approved overtime lands in one of them by the calendar. The company can rename and re-rate these, never remove them. It can also add its own types (for example a night shift at 1.25) that an employee picks on an overtime request, or that is typed on a payroll run. A policy can pay a type at its own multiplier instead of the company's: the three otRate… fields for the built-in ones, overtimeRates for the company's own.

For one employee, the multiplier is the policy's own if it has one, else the company's. Every overtime type object has the same shape, below.

FieldTypeMeaning
idstringOvertime type id.
namestringAs the company calls it.
kindstringNORMAL_DAY, REST_DAY or PUBLIC_HOLIDAY for the built-in three; CUSTOM for the company's own. Never changes.
multipliernumberThe company-wide multiplier, e.g. 1.50.
isArchivedbooleanOnly a custom type can be archived.
Who may write. Any Admin or Owner, and any key with policies:write, may add, edit or archive an overtime type. There is no owner-only check on these endpoints, unlike creating, archiving or restoring a policy.

Module gate for all four: the policies module on the plan, else 403. The read does not check a per-admin grant, so for a key only the plan matters.

PUT /overtime-types/{id} policies:write

Rename an overtime type or change its company-wide multiplier. This works on the built-in three too (their kind never changes).

Request

id in the path is the overtime type id. The body is the same as POST /overtime-types.

Both fields are required and replaced, so send the name and multiplier you want to keep. Changing the multiplier marks every generated payroll draft stale, so regenerate them before they are submitted; a rename alone does not. A policy that has its own multiplier for the type is not affected. Payslips already filed keep the name and rate they were generated with.

Response 200

The updated overtime type object.

curl -X PUT https://<api-host>/overtime-types/ot_type_123 \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Night shift", "multiplier": 1.50 }'

Errors

  • 400 { "errors": { … } } a field failed validation, as for POST.
  • 400 { "message": "There's already an overtime type called \"Night shift\"." } another non-archived type has that name.
  • 404 no overtime type with that id in this company (empty body).
  • 403 the key lacks the scope, or the plan lacks the module.
POST /overtime-types/{id}/archive policies:write

Stop offering one of the company's own overtime types. There is no restore endpoint.

Only a custom type can be archived. Archiving does not touch overtime already requested or typed on a payroll run: that is still paid, at the type's name and rate. The type simply stops being offered on new requests (GET /overtime/types).

Response 200

The overtime type object, with isArchived: true. No request body. Archiving an already archived type succeeds again.

curl -X POST https://<api-host>/overtime-types/ot_type_123/archive \
  -H "Authorization: Bearer wp_live_xxx"

Errors

  • 400 { "message": "\"Normal day\" is built in: approved overtime lands in it by the calendar, so it can't be removed." } the id is one of the built-in three.
  • 404 no overtime type with that id in this company (empty body).
  • 403 the key lacks the scope, or the plan lacks the module.

Not available to API keys

GET /policies/mine/modules (which modules the signed-in employee's own policy allows) is for people only and answers 403 to any key.
