Policies

Employee policies (attendance rules, overtime, leave entitlements) and the one-call bulk setup an integration sends when it provisions a company.

Policies

A policy is a bundle of rules an employee is put on: which self-service areas they can use, how clock-in is checked, how overtime is calculated and paid, and how many days of each leave type they get. Everyone not assigned a policy falls back to the company's default policy. A new company starts with two, Monthly Workers and Hourly Workers.

PUT /policies/{id} replaces the whole policy. Any field you leave out goes back to its default (see the table below), including every switch and every overtime rate, and leaveEntitlements is replaced by what you send, so omitting it empties the policy's entitlements. Read the policy with GET /policies, change what you need, and send the whole thing back.

Policy endpoints:

GET /policies policies:read

Every policy in the company, archived ones included, ordered by name.

Module gate: the policies module, held to the plan only. Unlike the write endpoints, an admin grant that leaves Policies out does not block this read, because other screens use it as a lookup.

curl -X POST https://<api-host>/policies \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Office Staff",
    "salaryType": "MONTHLY",
    "otDailyThresholdMinutes": 480,
    "otRateNormalDay": 1.5,
    "leaveEntitlements": [{ "leaveTypeId": "leavetype_123", "defaultDays": 14 }]

Errors

  • 400 a field failed validation ({ "errors": { … } }), e.g. a missing or over-long name, or a value outside its range.
  • 400 { "message": "A policy named \"Office Staff\" already exists." }. Note this shape: message, not error.
  • 403 the key lacks the scope, or the plan / admin access lacks the module.
PUT /policies/{id} policies:write

Replace a policy's settings and leave entitlements.

Module gate: the policies module. A plan without it gets 403; so does a key whose admin access leaves Policies out (Your admin access doesn't include the 'policies' module.).

Request

id in the path is the policy id. The body is the same as POST /policies.

This is a full replace, not a merge: omitted fields revert to the defaults listed for POST /policies, and leaveEntitlements is replaced wholesale (an omitted or empty list removes them all). It does not change isDefault or isArchived; use the endpoints below for those.

Response 200

The updated policy, as for POST /policies.

curl -X PUT https://<api-host>/policies/policy_123 \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Office Staff",
    "salaryType": "MONTHLY",
    "otRateNormalDay": 1.5,
    "leaveEntitlements": [{ "leaveTypeId": "leavetype_123", "defaultDays": 16 }]
  }'

Errors

  • 400 a field failed validation ({ "errors": { … } }), e.g. a missing or over-long name, or a value outside its range.
  • 400 { "message": "A policy named \"Office Staff\" already exists." }. Note this shape: message, not error. Another policy already has that name.
  • 404 no policy with that id in this company (empty body).
  • 403 the key lacks the scope, or the plan / admin access lacks the module.
POST /policies/{id}/default policies:write

Make a policy the company default.

Module gate: the policies module. A plan without it gets 403; so does a key whose admin access leaves Policies out (Your admin access doesn't include the 'policies' module.).

The previous default is cleared, so there is exactly one. An archived policy cannot be made the default.

Response 200

The updated policy, as for POST /policies. No request body.

curl -X POST https://<api-host>/policies/policy_123/default \
  -H "Authorization: Bearer wp_live_xxx"

Errors

  • 404 no such policy in this company, or the policy is archived (empty body).
  • 403 the key lacks the scope, or the plan / admin access lacks the module.
POST /policies/{id}/archive policies:write

Archive a policy.

Module gate: the policies module. A plan without it gets 403; so does a key whose admin access leaves Policies out (Your admin access doesn't include the 'policies' module.).

Archiving the default policy also clears its default flag, and nothing replaces it, so the company is left with no default until you call POST /policies/{id}/default on another. Employees assigned to the policy are not reassigned.

Response 200

The updated policy, as for POST /policies. No request body.

  -H "Authorization: Bearer wp_live_xxx"

  • 404 no such policy in this company (empty body).
  • 403 the key lacks the scope, or the plan / admin access lacks the module.

Bulk setup

One call that sets a company's working days, pay calculation, overtime rates, working hours and leave entitlements, for an integration that has just created the company and collected the client's answers. Every block is optional; send only what the client answered.

PUT /onboarding organizations:write policies:write leave:write

Apply the company's initial policy, working-time and leave setup in one request.

Scopes: the key needs all three scopes above, not one of them. Module gate: none, so it works whether or not the plan includes the Policies module.

Check for support first. A deployment advertises this endpoint by listing onboarding.bulk in features on GET /whoami. Probe that before relying on it, rather than finding out from a failed call.

Request

A JSON object with up to five optional blocks: settings, calculation, overtime, workSchedule, leave. The fields below are written as block.field.

settings.nonWorkingDaysstring[]NoWeekday names that are not worked; the rest become working days.
calculation.prorationBasisstringNoTWENTY_SIX or CALENDAR (case-insensitive): the day count a month is divided into when pro-rating pay.
calculation.hrdf.contributebooleanNoWhether the company contributes to HRDF.
calculation.hrdf.ratenumberWhen contribute is trueMust be greater than 0 when contributing.
overtime.normalDay, overtime.restDay, overtime.publicHoliday, overtime.restDayInShift, overtime.publicHolidayInShiftnumberNoOvertime multipliers. overtime.dailyThresholdMinutesnumberNoAccepted but not applied by the current code (see the note below).

Response 200 or 409

200 when every block you sent was applied; 409 when at least one failed. Both carry the same body:

FieldTypeMeaning

policiesUpdatedstring[]Ids of the policies the overtime block touched.
leaveTypesUpdatedstring[]Codes of the leave types the leave block changed.
 
{
  "applied": ["settings", "overtime", "leave"],
  "failed": [],
  "policiesUpdated": ["policy_123", "policy_456"],
  "leaveTypesUpdated": ["ANNUAL"]
}

Things that bite

It is not atomic. Blocks run in a fixed order (settings, calculation, overtime, workSchedule, leave) with no surrounding transaction, and one failing does not stop the rest. On a 409, the blocks listed in applied did land. Fix the cause and re-send the same body: every block is idempotent, so the ones that already applied simply apply again.
Overtime goes to every non-archived policy, not just the default. A new company has two policies (monthly and hourly), and setting rates on one would leave the other on statutory rates. That also makes this a provisioning tool: after go-live, use PUT /policies/{id} per policy, because re-sending this would flatten policies an admin set apart on purpose.
  • The body is checked before anything is written. A bad request returns 400 and changes nothing.
  • An empty body {} returns 200 with empty lists.
  • Leave codes that don't match one of the company's leave types are skipped silently, with no error. Check leaveTypesUpdated to see what was matched. A new company starts with ANNUAL, MEDICAL, COMPASSIONATE, HOSPITALIZATION, MARRIAGE, MATERNITY, PATERNITY and UNPAID.
  • The leave block writes the leave types directly. It does not run the checks the leave-type endpoints make (such as carry-forward only on ANNUAL, or no negative days), so a value you send is stored as sent.
  • overtime.dailyThresholdMinutes is accepted in the body but the current code does not write it to any policy. Set the threshold with PUT /policies/{id} (otDailyThresholdMinutes).
  • The settings block writes working days to the organization; the calculation block writes the pro-rating basis and HRDF settings to the payroll settings, creating them if the company has none yet.
curl -X PUT https://<api-host>/onboarding \
  -H "Authorization: Bearer wp_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "settings": { "nonWorkingDays": ["SATURDAY", "SUNDAY"] },
    "calculation": { "prorationBasis": "TWENTY_SIX", "hrdf": { "contribute": true, "rate": 1.0 } },
    "overtime": { "normalDay": 1.5, "restDay": 2.0, "publicHoliday": 3.0 },
    "workSchedule": { "workingHoursStart": "09:00", "workingHoursEnd": "18:00", "lunchBreakMinutes": 60 },
    "leave": {
      "entitlements": { "ANNUAL": 16, "MEDICAL": 14 },
      "carryForward": { "ANNUAL": { "enabled": true, "expiryMonth": 3, "maxDays": 5 } }
    }
  }'

Errors

  • 400 { "message": "…" } the body was refused before anything ran: both workingDays and nonWorkingDays sent; a name that is not a weekday; hrdf.rate not above 0 when contribute is true; an unknown prorationBasis; expiryMonth missing on an enabled carry-forward. Note message, not error.
  • 400 { "errors": { … } } expiryMonth outside 1 to 12.
  • 409 some blocks applied and some failed. The body is the response above, not an error object.
  • 403 the key lacks one of the three scopes.

Not available to API keys

GET /policies/mine/modules (which modules the signed-in employee's own policy allows) is for people only and answers 403 to any key.
